# `mariadb` — application database

> **Target state.** This page describes the system as it is meant to be. The
> remaining code work is tracked in [`IMPLEMENTATION.md`](../../IMPLEMENTATION.md).
> When this page and the code disagree, this page is authoritative.

## What this role is for

`mariadb` runs the relational database that stores the Frappe site. It owns the database container, its data volume, its startup encryption and its health check. It does not initialise the site; the `erp` role does that through the one-shot `configurator` service, which uses the root credential only for site creation.

The database is never reachable from the internet. It joins only `erp-db`, an internal network with no gateway, and publishes no host port. It is not on the application network or the cache network.

## Database identities

MariaDB has two kinds of identity, with different lifetimes.

| Identity | Used by | Lifetime | Credential location |
|---|---|---|---|
| `root` | The one-shot configurator for `bench new-site`, and local recovery | Provisioning and break-glass only | `<base_dir>/mariadb/secrets/db_root_password` |
| Frappe site user | Backend, workers and scheduler at runtime | Created once with the site | The site's `site_config.json` |

Frappe creates the site database and a dedicated database user. `bench new-site`
chooses the database name unless `--db-name` is passed; the name is not necessarily
`frappe`. In v15 the user name defaults to the database name; from v16 it may be
the explicit `db_user`. The password is generated by Frappe. The grant is limited
to that one database, and the user's host scope is restricted to the Docker address
pool with `--mariadb-user-host-login-scope='172.30.%.%'`. Read `.db_name` and
`.db_user // .db_name` from `site_config.json`; do not hardcode either.

The runtime services read the site user from `site_config.json`. They never read
the root secret. The root secret is mounted only into the MariaDB container and
the one-shot configurator. MariaDB starts with
`MARIADB_ROOT_PASSWORD_FILE=/run/secrets/db_root_password`; the configurator reads
the same path. The secret is a Compose `file:` secret, not a Swarm secret, so it
does not appear in `docker secret ls` and is not encrypted by Docker. The host
file mode is the protection. See
[ADR-024](../DECISIONS.md#adr-024--the-mariadb-root-credential-is-for-provisioning-only).

## Startup and encryption

MariaDB starts with a shell wrapper. The wrapper prepares the key material in a temporary filesystem, then starts the real database process.

The sequence is:

1. Create `/etc/mysql/encryption` in `tmpfs`.
2. Base64-decode `DB_ENCRYPTION_KEY` into `keyfile`.
3. Write `DB_KEY_PASSWORD` into `keyfile.key`.
4. Encrypt `keyfile` with OpenSSL AES-256-CBC, producing `keyfile.enc`.
5. Start `mariadbd` with the `file_key_management` plugin and the encrypted key file.
6. Enable InnoDB table encryption, log encryption, temporary disk table encryption and temporary file encryption.
7. Apply UTF-8 settings and disable symbolic links.

The key material is not written to the persistent volume. It is reconstructed from the container environment at each start. This means the vault must be available when the container is recreated; it is not available to a normal application deploy.

### Database settings

| Setting | Value | Why |
|---|---|---|
| Character set | `utf8mb4` | Store the full Unicode range |
| Collation | `utf8mb4_unicode_ci` | Consistent sorting and comparison |
| `skip-character-set-client-handshake` | enabled | Ignore a client's older charset request |
| `skip-innodb-read-only-compressed` | enabled | Avoid a compatibility problem with compressed read-only tables |
| `file_key_management` | enabled | Use an external key file |
| `innodb-encrypt-tables` | `ON` | Encrypt table data |
| `innodb-encrypt-log` | `ON` | Encrypt the redo and undo logs |
| `innodb-encryption-threads` | `4` | Parallel encryption work |
| `encrypt-tmp-disk-tables` | `ON` | Encrypt temporary tables written to disk |
| `encrypt-tmp-files` | `ON` | Encrypt temporary files |
| `innodb-buffer-pool-size` | `1G` | Working memory for the database |
| `skip-symbolic-links` | enabled | Prevent a table from pointing outside the data directory |
| `MARIADB_AUTO_UPGRADE` | `1` | Apply compatible internal upgrades on startup |
| `MARIADB_ROOT_PASSWORD_FILE` | `/run/secrets/db_root_password` | Read the root password from the Compose secret, not the environment |

The `1G` buffer pool is a fixed setting. The host has swap as an OOM safety net, but the pool size should be reviewed if the server's memory changes.

## Security invariants

- MariaDB has no published host port.
- It joins only `erp-db`, which has no gateway to the internet.
- It is not a member of `erp_default`, `erp-cache`, `traefik-public`,
  `docker-proxynet` or `crowdsec-net`.
- The root password lives in a `0600` file owned by `deployowner`; it is not in
  the application `.env` or the runtime service environment.
- The one-shot configurator is the only application-side service that receives
  the root secret, and it exits after site creation.
- The runtime database user is the per-site Frappe user, not `root`.
- The encryption keyfile and its password are held in `tmpfs`, not on the data volume.
- InnoDB tables, logs and temporary files are encrypted at rest.
- Symbolic links are disabled.
- The container runs with `no-new-privileges`.

## The backup interface

`backup` resolves the database name from `sites/<site>/site_config.json` and reads
the database through the MariaDB container:

```bash
DB_NAME="$(docker compose -f <base_dir>/erp/compose.yaml exec -T backend \
  jq -r .db_name sites/<site>/site_config.json)"

docker exec mariadb-database sh -c \
  'MYSQL_PWD="$(cat /run/secrets/db_root_password)" \
   exec mariadb-dump -uroot ... "$1"' sh "$DB_NAME"
```

The backup process reads the secret from inside the container. It does not receive
the root password in its own environment or on a host command line. It fails closed
if `site_config.json` is missing or `.db_name` is empty; it does not fall back to a
hardcoded `frappe`.

The dump is a logical backup: it contains the schema and data, not the physical
InnoDB files. A restore therefore needs the matching sites-volume archive from the
same backup run. That archive contains `site_config.json` and is a secret in its
own right.

### Restoring

The high-level order is:

1. Stop the application services so nothing writes during the restore.
2. Restore the logical dump into MariaDB.
3. Restore the sites volume.
4. Start the application and run smoke checks.

The recovery procedure is in [`RESTORE.md`](../RESTORE.md).

## Idempotency and change behaviour

- The Compose file and `.env` are rewritten when their content changes.
- The data volume is persistent. Re-running the role does not delete data.
- `MARIADB_AUTO_UPGRADE=1` allows compatible internal upgrades when the image version changes. Take a backup before a major version change.
- Changing `vault_db_root_password` alone does not change the database user. The password must be changed inside MariaDB first, then the secret file must be rewritten and the container restarted.
- Changing the encryption key requires a deliberate migration. Do not rotate it as if it were an ordinary password.
- The health check is the readiness gate used by both `site.yml` and `update.yml`
  before the application starts.

## Verification

```bash
docker ps --filter name=mariadb-database
docker inspect --format '{{.State.Health.Status}}' mariadb-database
docker exec mariadb-database healthcheck.sh --connect --innodb_initialized
docker exec mariadb-database sh -c \
  'MYSQL_PWD="$(cat /run/secrets/db_root_password)" \
   exec mariadb -uroot -e "SHOW DATABASES;"'
docker exec mariadb-database sh -c \
  'MYSQL_PWD="$(cat /run/secrets/db_root_password)" \
   exec mariadb -uroot -e "SELECT User, Host FROM mysql.user;"'
docker volume inspect mariadb-data
```

Expected results:

- The container is running and healthy.
- The database list includes the `db_name` recorded in the site's
  `site_config.json`, not necessarily a database called `frappe`.
- The user list includes the per-site Frappe user with a host scope inside
  `172.30.%`, not a wildcard `%`.
- The volume exists and is mounted at `/var/lib/mysql`.
- No host port is published.

Check encryption is active:

```bash
docker exec mariadb-database sh -c \
  'MYSQL_PWD="$(cat /run/secrets/db_root_password)" \
   exec mariadb -uroot -e "SHOW VARIABLES LIKE '\''innodb_encrypt_tables'\'';"'
```

## Failure modes

| Symptom | Likely cause | First check |
|---|---|---|
| Container restarts in a loop | Key material is invalid, or the data directory is from an incompatible version | `docker logs mariadb-database` |
| `Access denied` from the application | The per-site user in `site_config.json` does not match the database grant, or the site database is missing | Check the user and host scope in MariaDB; inspect the site's `site_config.json`; confirm the configurator's site creation completed |
| The one-shot configurator cannot create the site | The root secret is missing or stale, or `erp-db` membership is wrong | `docker logs configurator`; inspect `erp-db`; check the root secret file mode and contents |
| Health check never becomes healthy | InnoDB is still recovering, or the disk is full | `docker logs`; `df -h`; `docker exec ... healthcheck.sh` |
| `Can't create/write to file` | The data volume is read-only or the disk is full | `docker inspect` mounts; `df -h` |
| High memory use | The 1G buffer pool plus the host workload exceeds RAM | `free -h`; `docker stats` |
| Backup dump fails | Root password mismatch, `site_config.json` is missing, or the `db_name` in it does not exist | Run the backup manually and read the log; check the site config before the dump |

## Changing the database

### Change the root password

1. Take a backup.
2. Change the password inside MariaDB with `ALTER USER`.
3. Update `vault_db_root_password`.
4. Run `playbooks/site.yml` to rewrite the root secret file and restart.
5. Verify the application and a manual backup.

The application does not restart with the new root password; it continues to use
the per-site user from `site_config.json`.

### Change the image version

1. Take a backup.
2. Read the MariaDB release notes.
3. Update `mariadb_image`.
4. Run `playbooks/site.yml` in development.
5. Verify the schema and the application.
6. Apply in production.

Do not jump across a major version without checking the upgrade path.
